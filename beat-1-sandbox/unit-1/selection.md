\## Reflection



\### Run history



I started by thinking about what would actually make an issue good for a first contribution. I focused on whether the repo was still active, whether the issue was recent, whether the task was clear, and whether someone else was already working on it.



I went through a couple versions of the rubric before getting to the final one. At first some of my checks were too general. I changed them so they looked at facts that could actually be checked. For example, instead of just saying a repo should be active, I checked recent commits and repo activity. I also made the issue scope check more important because that was the main thing that separated the three issues.



\### Issue analysis



For issue #1, my rubric gave it an accept verdict. This matched the gold label.



The issue passed all of my checks. It was still open and it was created recently. The repo also had recent commits, including commits from September 16, 2026. The issue had no comments, no assignees, and there were no pull requests in the repo when I checked it.



The biggest reason I liked issue #1 was that the problem was very specific. It explains that `\_check\_skip()` is passing `"IngestedSource"` as a string instead of using the actual model class. It also tells me which files are related to the problem. That gives me a clear place to start without needing to understand the entire project first.



\### Check rationale



One check from my rubric was \*\*"Issue is scoped."\*\*



I included this because I think a first issue should have a clear problem that I can understand before I start coding. I wanted the issue to describe one specific bug or task instead of asking for a large feature with a lot of decisions left open.



Issue #1 passed this check because it explains the bug, the cause of the bug, and the files involved. Issue #2 did not pass because adding support for an entire portfolio website could involve a lot of choices that were not explained in the issue.



\### Trade-offs



The hardest part was deciding what counts as a good threshold. A repo can still be maintained even if there has not been a commit in the last few weeks. At the same time, I did not want to choose an issue from a repo that nobody works on anymore.



It was also hard to decide how strict the scope check should be. If I made it too strict, I could reject issues that are still reasonable for a beginner. If I made it too loose, almost every issue would pass.



If I did it again, I would probably make the scope check even more specific. The other checks passed pretty easily for all three issues because this repo is active and the issues are new. The scope check was the part that actually helped me decide which issue would be the best fit for a first contribution.
