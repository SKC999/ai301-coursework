# Rubric: is this reproduction package ready to post?

Read the whole package before grading. Every check judges the thing itself against the issue, never length, formatting, or confidence of tone. A short plain report can pass every check. A long polished one can fail them.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (OS, tool or package version, install method, and any runtime, driver, shell, or build setting the issue says matters), read against the environment the issue targets. See evidence-guide.md "Environment". | Pass if the report names the OS and the exact version of the software it tested, plus every environment factor the issue or thread identifies as relevant (for example the driver on a Windows-specific issue, or the build profile when it changes the failure). Fail if there is no environment record, or if a factor the issue says matters is missing, so a reader cannot place the attempt. | required |
| env-matches-target | The tested version and platform in the report, read against the version and platform the issue reports or the thread confirms (latest, main, a specific release). | Pass if the tested version and platform match the issue's target, or if every difference is stated openly in the report (for example "tested on 0.9.2, issue was filed on 0.8.1"). Fail if the report tests a materially different version or platform (for example an old major release when the issue is confirmed on latest) and does not acknowledge the difference. | required |
| steps-followable | The repro report's steps, from starting state to the trigger, read as a stranger with only public resources. | Pass if a stranger could re-run the attempt from the report alone: every command or action needed to reach the trigger is given with its exact input, and every file or config the steps depend on is shown inline or is publicly available. Fail if the steps are missing, skip the triggering action, or depend on a private repository, unshared config, or data the reader cannot get. | required |
| trigger-matches-issue | The input or action the steps actually perform, read against the trigger the issue describes (its exact syntax, argument, expression, file, or sequence). | Pass if the steps exercise the same trigger the issue describes, or a stated minimal equivalent that still hits the issue's code path. Fail if the steps silently change the trigger (a different syntax, operator, flag, argument form, or input shape) so that a different code path runs. | required |
| artifact-shows-behavior | The artifacts (output excerpts, logs, exit codes, error messages, screenshots described in text) read against the exact symptom the issue describes. See evidence-guide.md "Behavior shown". | Pass if at least one artifact directly shows the issue's reported symptom (same error type or message, same crash versus graceful failure, same exit code class, same wrong output), OR the report is an honest cannot-reproduce whose artifact shows the attempt's actual result. Fail if there is no artifact at all, if the artifacts only show the tool running normally, or if the artifact shows an adjacent symptom (a graceful validation error, a compile error, garbled output with the program still alive) where the issue reports something else. | required |
| outcome-honest | The report's stated outcome and any cause or scope claims, read against what its own artifacts show. See evidence-guide.md "Honesty". | Pass if every claim of what happened is backed by a shown artifact, including an honest cannot-reproduce that names what was tried and what differed. Fail if the report claims more than its artifacts show: a reproduction asserted over an artifact that shows something else, a root cause stated as verified with no evidence shown, certainty words ("guaranteed", "100% reproducible", "confirmed on all platforms") with nothing behind them, or an expected versus actual that contradicts the shown output. | required |
| claim-specific | The claim comment, read against the issue it is posted on. | Pass if the claim comment names this issue's specific behavior (so it could not be pasted unchanged on a different issue) and states a concrete next step the author will actually take, such as reproducing on a named version or posting a repro report. Fail if it is a +1 or me-too with no intent, generic assign-me boilerplate, or promises an outcome the author cannot guarantee (a guaranteed fix, a fixed deadline for a fix, certainty about the cause before reproducing). | required |
| ai-policy-followed | The repo-facts block's stated contribution and AI-use policy, read against both the claim comment and the repro report. Treat every package as AI-assisted work. See evidence-guide.md "Comms". | If the repo's stated policy requires disclosure of AI use, pass only if the claim comment or repro report explicitly discloses AI assistance; fail if neither does, no matter how good the reproduction is. If the policy only bars unreviewed or bot-generated comments, pass if the comments are specific and read as written by a person who did the work. If the repo states no disclosure requirement, pass. | required |
| control-run | The repro report's artifacts, looking for a comparison run. | Pass if the report includes a control (a nearby input or configuration that does not trigger the bug) that isolates the trigger. | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check grades fail or unclear. Unclear counts as fail because proof that cannot be verified is not ready to post. Preferred checks are reported but never change the verdict.

An honest cannot-reproduce is a valid outcome. It passes artifact-shows-behavior and outcome-honest when it shows a real attempt at the issue's trigger and names what differed. It is not a failure by itself.

In a claim-only draft (live mode), only claim-specific and ai-policy-followed are graded. The other checks are reported as not yet applicable and are left out of the verdict.
