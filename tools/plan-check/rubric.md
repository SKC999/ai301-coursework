# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| grounded-cause | The plan's stated cause read against every step, control run and artifact in the repro evidence (and any maintainer finding in the thread highlights) | Pass if the stated cause explains the actual behavior the repro shows and no step or control in the repro evidence rules that cause out. Fail if a control run shows the blamed component working, if the evidence pins the failure somewhere the plan does not look, or if the plan names no cause at all. | required |
| bounded-scope | The plan's change, approach steps and in-scope list read against what the issue and repro evidence actually ask to fix | Pass if every piece of planned work is needed to fix the reproduced behavior or to test that fix. Fail if the plan also commits to work the issue does not need, such as a rewrite or redesign, a dependency or framework migration, a new option or setting, UI changes or a refactor of neighboring code. Explicitly deferred or out-of-scope work does not count against it. | required |
| executable | The plan's files, functions and approach steps | Pass if a stranger could start the change today because the plan names where the change goes (a file, function or code site) and one chosen approach. Fail if the plan leaves the location or the approach to be decided at build time, for example "somewhere", "not sure which layer", "whichever is easier" or "profile first and then optimize". | required |
| decisive-test | The plan's test plan read against the repro evidence's steps and expected result | Pass if the test plan names at least one specific observable outcome that would show this fix worked, such as a repro step re-run with a stated expected result or a named regression test with its expected pass. Fail if the only test is "run the full suite", "nothing else breaks", "should feel faster" or any check with no stated expected result for the fixed behavior. | required |
| thread-direction | The plan and plan comment read against the thread highlights, looking for an explicit maintainer or owner direction (a chosen approach, an isolated culprit, a rejected approach, a request to test a patch) | Pass if the thread holds no such direction, or if the plan or comment follows it or names it and says why it departs. Fail if a maintainer gave explicit direction and the plan and comment neither follow nor engage it. | required |
| policy-disclosure | The plan comment read against the repo-facts contribution policy, treating every package as AI-assisted work | Pass if the repo states no AI disclosure requirement, or if the comment discloses AI use the way the policy asks. Fail if the policy requires disclosing AI use and the comment contains no disclosure. | required |
| honest-unknowns | The plan's risks and unknowns read against what the repro evidence leaves untested | Pass if the plan names at least one real uncertainty or untested case, or if the repro evidence leaves nothing material open. Fail if the plan states as fact something the evidence does not show. | preferred |

## Verdict rule

The verdict is accept only when every required check grades pass. One required fail makes the verdict reject. An unclear grade on a required check counts as a fail because a plan we cannot verify from the package is not ready to build from. Grade unclear only when the package truly holds no evidence for that check. If evidence is present the grader must decide pass or fail. The preferred check never changes the verdict and is reported in the summary only.
